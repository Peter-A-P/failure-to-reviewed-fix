Measured on 120 real bugs, judged by tests no model saw

An AI that fixes two real bugs in three before a person even looks, and proposes a pull request only when it is confident.

When software breaks, someone has to find out why and write the fix, and that can take days. This project hands the first draft to AI: it groups the error messages into one problem, writes a test that proves the bug before touching the code, drafts a fix, and has a second AI from a different company try to break it. Then a person decides. It was measured on {{tasks}} bugs from public Python projects, each judged by tests the maintainers wrote and no model saw.

How it works

Seven steps, each checked before the next

The rest of this page is the whole method, in the order it happens. Each part starts in plain language, with a picture. Where there is more to say for someone who does this for a living, it is folded away under For the technical reader, so you can skip it if you only want the idea.

The whole idea in one picture

One broken change usually sets off many alarms. The pipeline turns them into one problem, proves the problem with a test, fixes it, has the fix attacked, and then decides how loudly to speak. Nothing it produces is merged; at most it offers a fix.

  1. 1CaptureEach failure becomes one record, with its error and where it happened.
  2. 2GroupRecords with one cause become one ticket.
  3. 3LocateA small, cheap model finds the files most likely at fault.
  4. 4ProveA new test must fail on the broken code, or the run stops.
  5. 5FixThe fix must pass that test and every test that passed before.
  6. 6ChallengeA model from another company is asked to find what is wrong.
  7. 7RouteOffer it, suggest it, or say nothing.

No step can be skipped. No fix is written until a test has failed, no fix is offered while the reviewer objects, and there is no step at all that merges. The code enforces each of those rules, and a test checks each one.

Twenty alarms, one bug

When a live system breaks, a dozen measurements jump at once, each its own alarm with its own name. Nothing in the words "dead letters rose" and "request latency fell" says they are the same problem. Only the timing does. The first design compared alarms one at a time and found almost nothing; grouping them by when they started, and then by their pattern, found most of the causes.

Grouping by incident first wins on all {{chaos_wins}} of {{chaos_folds}} splits. Its average agreement with the true faults is {{ari_two_stage}}, against {{ari_record}} for comparing alarms one by one, which is chance.

What these numbers do not say. With tracebacks it finds about half of each fault ({{faults_completeness}} completeness). With people's bug reports, where only the words are left, it needs a trained text model ({{duplicates_ari_encoder}}, against {{duplicates_ari_hash}} without one), and that model was tried after the first result was seen. None of the three sets has two incidents overlapping in time.

For the technical reader: the two clustering methods and how they were scored

The record-level method builds one distance per pair of records from three channels: a fingerprint (exception type, innermost project frame, normalised message), an embedding of the failure text, and code locality (shared frames and files). Average-linkage clustering cuts it at a threshold tuned on held-out causes. The two-stage method first groups records whose start times fall together into incidents, then groups incidents by the set of their symptoms. Quality is the adjusted Rand index (ARI), purity and completeness. On 09's runs, every one of the {{chaos_folds}} ways of holding three of eight faults out was scored; on the other two sets, five folds by cause with a delete-one-cause jackknife for the interval. The full write-up of the rejected method is in docs/rejected.md.

No fix without a failing test first

Before the fixer may touch the code, another step writes a new test that shows the bug, and runs it on the broken code in a sealed container. If the test passes there, it proves nothing, and the run stops. The fixer is then held to that test and to every test that passed before. The idea is that a fix should come with its own evidence.

For the technical reader: how the rule is enforced, and how the comparison was run

The pipeline is a state machine with no transition into "patched" except from "test failed as expected", observed in the sandbox; a test that errors rather than fails, or passes on the broken commit, gets one retry that is told why, then the run stops. The ablation ran outside the graph, so the graph keeps no switch that turns the rule off, on {{ablation_tasks}} of the main run's tasks drawn with a fixed seed, reusing the main run's localisation, and went through project 03's release gate as a paired comparison at a ten-point margin.

A second AI, from another company, tries to break it

The fix is written by Anthropic's model. It is then reviewed by OpenAI's, which is told to find what is wrong with it. The idea is that two models from different companies share fewer blind spots. When the reviewer objects, the fix can still be suggested, but it is never offered as ready.

An objection is a real warning. When the reviewer objected, the fix was wrong {{wrong_objected_pct}} of the time ({{objected_count}} fixes); when it agreed, {{wrong_agreed_pct}} ({{agreed_count}} fixes).

The different-company rule is not proven. The fixer's own company's model objected less often, so it raised fewer false alarms and caught fewer bad fixes, and its confidently-wrong rate would have been {{same_wrong_auto_pct}}. Project 03's release gate could not tell the two reviewers apart. The rule stays as a design choice the evidence leans towards.

For the technical reader: how the vendor split is enforced

Each role is an alias in the portfolio gateway (project 04). At start-up the pipeline resolves the fixer and reviewer aliases and refuses to run if they land on the same provider, and a test asserts it against the shipped configuration. The same-vendor arm reviewed all {{reviewed}} reviewed patches again on identical input, and the different-vendor reviewer was also asked again, to measure how much a reviewer disagrees with itself.

Knowing when to stay quiet

A wrong fix presented as ready wastes an engineer's time, so each fix is routed by its evidence: did the new test pass, did every old test still pass, did the reviewer agree. Only a fix with all three is offered as a pull request. A weaker one is left as a suggestion, and a run with no fix stays quiet. The rules were set on a separate 30 bugs before the main run.

The evidence sorts the fixes, but restraint costs a lot. Of the {{auto_count}} it offered, {{auto_hit_pct}} were right. Of the {{quiet_count}} it kept quiet about, {{quiet_right}} had a fix the hidden tests accepted, mostly where no old test covered the code it changed, which the rules read as "not shown safe".

For the technical reader: why the confidence score does not decide

The router also computes a confidence score with size penalties, and the plan was to calibrate a threshold on it against a 3% confidently-wrong target. On the validation split every patch that passed the rules scored the same, so the score did no work and the calibration landed on zero; changing it after seeing the main run would have been tuning on the test set. The rules decide, and that consequence was written down before the main run (docs/routing.md).

For the technical reader: how the evaluation avoids fooling itself

The subset was drawn with seed 20261017, 30 for calibration and 120 for the main run, and the sampler refuses to redraw once a run exists. Every drafted patch, whatever its tier, goes to the official SWE-bench harness, which runs the hidden tests in a Linux container; a task the harness could not judge is rerun, never counted as a failure. Proportions carry Wilson intervals and costs bootstrap intervals. The hidden tests and the maintainers' patches never reach a prompt.

On real pull requests

The same pipeline runs on two of my other projects, the release gate (03) and the AI gateway (04). When a pull request's tests fail, it reruns them in a sealed container, picks the biggest problem, and answers with a comment. It cannot push, open a pull request or merge, and it stops when that repository's US$1.50 is spent.

It found a real breakage nobody had planted. On its second run in 04, the biggest problem was not the planted bug but four tests broken by a spending limit set elsewhere. Its fix raised the limit, the reviewer objected that this weakened a deliberate safeguard, and it went out as a suggestion with the objection attached. The reviewer was right.

The same bug, two different answers. 04's planted bug was run twice on the same code. The 3% target

The plan allowed at most 3% of offered fixes to be wrong. It was {{wrong_pct}}, so the live version posts comments only.

The test step as a quality gain

A different company as the reviewer

Expected to catch more. The fixer's own company's model reviewed about as well, and the gate could not separate them.

A pass that tested nothing

The first live run in 04 ran no tests, because that repository leaves its tests out of its own image, and reported a pass. A run that tests nothing now fails.

A budget that forgot

The live spending total was meant to carry between runs in a cache the job was never allowed to write. It now travels in each run's own records.

What this does not do

The limits, stated as plainly as the results.

  • It never merges. There is no merge step in the code, and a test scans every source file to make sure none appears. On the live repositories it only comments.
  • It does not fix without proof. No failing test, no fix: the run stops and says why.
  • It does not meet its own target. {{wrong_pct}} confidently wrong is above 3%, so on this evidence it should suggest, not offer.
  • It is Python only, because the benchmark and the sandbox are.
  • It is not a production incident tool. The clustering was measured on recorded breakdowns, planted faults and old bug reports, with no two incidents at once.
  • It holds back good fixes. {{quiet_right}} of the {{quiet_count}} bugs it stayed quiet about had a fix that was right.

For the technical reader: the choices that are easy to get wrong
  • The sample was committed before the first run and the sampler refuses to redraw, so no hard task can quietly leave.
  • Every drafted patch is scored, whatever tier it was routed to, so the quiet tier's missed fixes are counted rather than invisible.
  • The benchmark harness runs in a Linux container, because on a Windows host even the benchmark's own reference patches fail.
  • Django and sympy, 61% of the benchmark, do not use pytest; the sandbox runs each project's own test runner and reads its output with the harness's parsers.
  • Every model call goes through the gateway with a US$1 cap per issue checked before the call, not after.
  • On live repositories the image build is the only step with network access, and it runs only the repository's own locked install.

How this was built

I designed this project and made the calls in it. I read the maintainers' hidden tests myself to classify the five wrong fixes, so that no model ever saw them. When the main run missed the 3% target, I decided the live version would post comments and never open pull requests. I chose my own repositories for the live trial and planted the bugs it was tested on, and I set its spending cap before the first call.

I used an AI coding assistant (Claude Code) for implementation and drafting, which is now standard practice in software, data science and machine learning work. Every number on this page can be reproduced from the repository.

Two pieces are my own earlier projects, reused as published: every model call goes through the AI gateway (project 04), and both experiments were judged by the release gate (project 03). The recorded breakdowns come from the real-time fraud and risk platform (project 09).

Glossary
Ablation
Running the system again with one part taken out, to see what that part was worth.
ARI (adjusted Rand index)
How well a grouping matches the true one. 0 is what random grouping scores and 1 is a perfect match.
Bootstrap interval
A range for a number found by resampling the data many times and seeing how far the number moves.
CI (continuous integration)
The automatic test run on every change to a repository. "ci fails" means some tests failed.
Confidently wrong
A fix the system was sure enough to offer as ready, which then failed the maintainers' hidden tests.
Gateway
One place every model call goes through, which picks the provider, records the cost and refuses a call once the cap is reached.
Hidden tests
The tests the maintainers wrote for their own fix. They are kept from every model and used only to mark the result.
LangGraph
A Python library for building multi-step AI workflows as a graph of steps.
Pull request
A proposed change to a repository, which a person reviews and accepts or rejects.
Release gate
A tool that compares two versions of a system on the same cases and decides whether the new one is worse by more than a set margin.
Sandbox
A sealed container with no network, where the tests and fixes run so they cannot reach anything else.
SWE-bench Verified
A public benchmark of 500 real GitHub issues from Python projects, each checked by people to be fair and solvable.
Ticket
One problem to fix, made from all the failures that share its cause.
Wilson interval
A range for a percentage that stays sensible when the count is small or near 0% or 100%.
